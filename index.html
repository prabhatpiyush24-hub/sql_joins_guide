What is a SQL JOIN?

A JOIN merges rows from two tables based on a matching column — like a shared customer_id appearing in both a Customers and an Orders table. The JOIN type controls which rows appear in the result.

📋 Customers Table — Left / Table A

customer_idnamecity
1AliceNew York
2BobChicago
3CharlieLos Angeles

📋 Orders Table — Right / Table B

order_idcustomer_idfood
1011Pizza
1022Pasta
10399 ⚠️Burger

⚠️ Key observation: customer_id 99 in Orders has no match in Customers. Charlie (ID 3) has no order. This mismatch is what makes each JOIN type behave differently.

1

INNER JOIN

Returns only rows where a match exists in BOTH tables — non-matching rows are excluded entirely

📖 Theory

Returns rows where a matching value exists in both tables. If a row in the left table has no match in the right table (or vice versa), that row is excluded entirely from the result.

🍽️ Restaurant Story

"You only get in if your name is on BOTH the reservation list AND the orders list."
  • ✅ Alice (ID 1) → ordered Pizza → IN
  • ✅ Bob (ID 2) → ordered Pasta → IN
  • ❌ Charlie → no order → OUT
  • ❌ Order #103 (ID 99) → no reservation → OUT
SELECT c.customer_id, c.name,
       o.food, o.amount
FROM   Customers c
INNER JOIN Orders o
  ON c.customer_id = o.customer_id;

📊 Result

customer_idnamefood
1AlicePizza
2BobPasta

✅ When to use: Only want rows with matching data on both sides — e.g., customers who have actually placed orders.

2

LEFT JOIN  (LEFT OUTER JOIN)

All rows from the LEFT table + matched rows from the right — unmatched right rows become NULL

📖 Theory

Returns ALL rows from the left table. Where a match exists in the right table, those columns fill in normally. Where no match exists, the right-side columns return NULL.

🍽️ Restaurant Story

"Show me ALL reserved customers — whether they ordered or not."
  • ✅ Alice → ordered Pizza → shown with details
  • ✅ Bob → ordered Pasta → shown with details
  • ✅ Charlie → no order → shown, food = NULL 🍽️
  • ❌ Stranger (order #103) → not on reservation list → excluded
SELECT c.customer_id, c.name,
       o.food, o.amount
FROM   Customers c
LEFT JOIN Orders o
  ON c.customer_id = o.customer_id;

-- Anti-join: customers with NO order
-- Add: WHERE o.customer_id IS NULL;

📊 Result

customer_idnamefood
1AlicePizza
2BobPasta
3CharlieNULL

✅ When to use: Keep all records from your primary table even if no related data exists — e.g., customers who haven't ordered yet.

3

RIGHT JOIN  (RIGHT OUTER JOIN)

All rows from the RIGHT table + matched rows from the left — unmatched left rows become NULL

📖 Theory

Returns ALL rows from the right table. Non-matching left rows become NULL. It is the mirror image of LEFT JOIN. Most developers rewrite RIGHT JOIN as a LEFT JOIN by swapping table order — same result, more readable.

🍽️ Restaurant Story

"Show me ALL orders that came in — reservation or not."
  • ✅ Order #101 (Pizza) → Alice has reservation → shown
  • ✅ Order #102 (Pasta) → Bob has reservation → shown
  • ✅ Order #103 (Burger) → no reservation → shown, name = NULL
  • ❌ Charlie → no order → excluded
SELECT c.customer_id, c.name,
       o.food, o.amount
FROM   Customers c
RIGHT JOIN Orders o
  ON c.customer_id = o.customer_id;

📊 Result

customer_idnamefood
1AlicePizza
2BobPasta
NULLNULLBurger

✅ When to use: Auditing — find orders with no matching customer (potential fraud or data entry errors).

4

FULL OUTER JOIN

All rows from BOTH tables — NULLs fill wherever there is no match on either side

📖 Theory

Returns ALL rows from BOTH tables. Where a match exists, columns fill normally. Where there is no match on either side, NULL fills the gaps. Essentially LEFT JOIN + RIGHT JOIN combined.

💡 MySQL does not support FULL OUTER JOIN — use a LEFT JOIN UNION RIGHT JOIN workaround.

🍽️ Restaurant Story

"I want the COMPLETE picture — every reservation AND every order tonight, matched or not."
  • ✅ Alice + Bob → matched perfectly
  • ✅ Charlie → food = NULL
  • ✅ Burger (ID 99) → name = NULL
  • Nobody is left out of this report.
-- PostgreSQL / SQL Server
SELECT c.name, o.food
FROM   Customers c
FULL OUTER JOIN Orders o
  ON c.customer_id = o.customer_id;

-- MySQL workaround:
SELECT c.name, o.food FROM Customers c
LEFT JOIN  Orders o ON c.customer_id = o.customer_id
UNION
SELECT c.name, o.food FROM Customers c
RIGHT JOIN Orders o ON c.customer_id = o.customer_id;

📊 Result

namefood
AlicePizza
BobPasta
CharlieNULL
NULLBurger

✅ When to use: Full data reconciliation — comparing two datasets to find records that exist in one but not the other.

5

CROSS JOIN

Every row from Table A paired with every row from Table B — the Cartesian product (M × N rows)

📖 Theory

Produces the Cartesian product. No ON clause needed. Every row from Table A is combined with every row from Table B. If Table A has M rows and Table B has N rows, the result has M × N rows.

🍽️ Restaurant Story

"Show every customer paired with every dish — every single combination."

3 customers × 3 dishes = 9 rows

Alice+Pizza, Alice+Pasta, Alice+Burger,
Bob+Pizza, Bob+Pasta, Bob+Burger,
Charlie+Pizza, Charlie+Pasta, Charlie+Burger

⚠️ Warning: 1,000 × 1,000 rows = 1,000,000 results. Can crash a database — always test on small data first!

-- Modern syntax
SELECT c.name, d.dish_name
FROM   Customers c
CROSS JOIN Dishes d;

-- Older equivalent (implicit cross join)
SELECT c.name, d.dish_name
FROM   Customers c, Dishes d;

📊 Sample Output (3 × 3 = 9 rows)

customer namedish
AlicePizza
AlicePasta
AliceBurger
BobPizza
… 5 more rows…

✅ When to use: Generating all combinations — products × sizes, test data, scheduling matrices (all staff × all shifts).

6

SELF JOIN

A table joined with itself using aliases — perfect for hierarchical and comparative data

📖 Theory

A table is joined with itself using table aliases to differentiate the two copies. Any JOIN type (INNER, LEFT, etc.) can be used. Common when a foreign key references the same table's own primary key.

🍽️ Restaurant Staff Story

The Employees table has everyone — but manager_id points back to another emp_id in the same table. The table must "look at itself" to find each person's manager name.

emp_idnamemanager_id
1Alice3
2Bob3
3Charlie 👑NULL
 
-- 'e' = employee, 'm' = their manager
-- Both aliases point to the SAME table
SELECT
  e.name  AS employee,
  m.name  AS manager
FROM   Employees e
LEFT JOIN Employees m
  ON e.manager_id = m.emp_id;

📊 Result

employeemanager
AliceCharlie
BobCharlie
Charlie 👑NULL (the boss)

✅ When to use: Org charts, category trees, social network connections, or comparing rows within the same table.

Quick Reference Summary

JOIN TypeLeft-onlyMatchedRight-onlyBest Used For
INNER❌✅❌Strict matches — customers with orders
LEFT✅✅❌All from left, even without a right-side match
RIGHT❌✅✅All from right — auditing unmatched records
FULL OUTER✅✅✅Complete reconciliation of two datasets
CROSS—All combos—Every possible pairing — sizes × colors × products
SELF—Same table—Hierarchies, org charts, same-table comparisons

✅ Best Practices

  • Always alias tables — c, o, e keeps queries readable and avoids column ambiguity
  • Start with INNER JOIN, switch to outer joins only when you intentionally need NULLs
  • Index your JOIN columns — unindexed joins cause slow full-table scans at scale
  • Use IS NULL after LEFT JOIN to find unmatched rows (anti-join pattern)
  • Avoid CROSS JOIN on large tables — results grow exponentially and can crash the DB

❌ Common Mistakes

  • Forgetting the ON clause — accidentally creates a massive CROSS JOIN
  • Joining on non-indexed columns — causes full table scans at scale
  • Using = NULL instead of IS NULL — NULL never equals anything in SQL
  • Adding WHERE on a right-table column — silently converts LEFT JOIN → INNER JOIN
  • Using FULL OUTER JOIN in MySQL without the UNION workaround
